# 0025. 记忆保留：条数上限与有界淘汰

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-10-31 |
| 决策者 | 项目所有者 |
| 关联 | 契约 §7.5（`memory` 接口）、§10（成本红线）、§11（失败降级）；ADR 0020（memory 落地） |

## 背景

ADR 0020 把 `memory` 落地成"只增不删"的单文件 SQLite：`write()` 插入、`retrieve()` 检索、没有删除路径。当时的判断是"长期运行缓慢增长，用户可手动删 `data/memory.db`"。

这个判断在桌宠场景里站不住：一次对话写 2 条（`user` + `pet`），一天几十轮就是上百条，几个月后库会到十万级，而 `retrieve` 的两条路径（FTS5 候选 80 条 + LIKE 全表扫）都会随行数线性变差；`LIKE` 尤其明显——它是逐词全表扫描。

用户要求：**超过 2000 条就删最旧的**，并且删除要同步清 FTS5、不阻塞主线程。

## 决策

### D1 上限 2000 行，按 `at` 升序淘汰

`MEMORY_MAX_ROWS = 2000`。超出部分从**最旧**的开始删：

```sql
DELETE FROM memories WHERE id IN (
  SELECT id FROM memories ORDER BY at ASC, id ASC LIMIT ?
)
```

`ORDER BY at ASC, id ASC` 而不是只按 `id`：`at` 允许调用方传入（`MemoryWrite.at`），同一批写入的 `user`/`pet` 共享同一个 `at`，按 `id` 兜底才能保证顺序稳定、删除可复现。

### D2 单次删除有界（≤200 行）

`MEMORY_PRUNE_BATCH_MAX = 200`。理由：`prune()` 是同步的（better-sqlite3 没有异步 API），如果一次删掉几万行，主进程会被卡住几百毫秒——而它跑在 IPC 回调链上，会连带卡住窗口消息。

有界之后最坏耗时锁在"删 200 行"这个量级（实测 2005 行的库删 5 行 ≈ 1ms，删 200 行 ≈ 4ms）。积压超过 200 时下次再删，几轮就收敛。

### D3 写后异步排期，不阻塞调用方

`write()` 落盘后调用 `schedulePrune()`：用 `setImmediate` 把 `pruneNow()` 推到当前事件循环之后，并用 `pruneScheduled` 标志合并同一批写入（一次对话的 `user` + `pet` 只会排一次）。

这满足两条约束：
- 契约 E-4 / I-3：`write()` 的同步耗时不因为淘汰而变长；
- 用户要求"不阻塞主线程"：删除本身仍然在主线程，但被推到了本轮 IPC 之后，且单次有界。

### D4 FTS5 由触发器同步，不手工删

`memories_fts` 是 external-content 表，`ensureFts()` 建了标准三触发器，其中 `memories_fts_ad AFTER DELETE` 会向 FTS 表发 `'delete'` 命令。所以 `DELETE FROM memories` 之后索引自动同步，**不需要也不应该**再手写一条 `INSERT INTO memories_fts(memories_fts) VALUES('delete', ...)`——那会双重删除。

单测直接数 `SELECT COUNT(*) FROM memories_fts`，断言它等于主表行数（2000），证明同步真的发生了。

### D5 `prune()` 进契约（§7.5）

它是模块的公开能力（自检与运维都要能主动触发），因此写进 §7.5 的接口表，随 1.6.0 一起升版。返回本次删除行数，便于日志与断言。

`snapshot()` 增加 `lastPrune: { at, deleted, rows } | null`，与 `lastRetrieve` 同一种"最近一次操作"的口径。

## 替代方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 按时间窗淘汰（保留最近 30 天） | 语义直观 | 久不对话时库会一直是空的；密集对话仍可能爆量 | 否 |
| 按重要度淘汰（`like:` 标签加权） | 保留偏好 | 需要定义权重与打分，且"重要"是主观的；本轮无数据支撑 | 否（记入未完成） |
| 后台定时器每小时 prune | 不占写入路径 | 违反 §12 的单定时器精神（虽然是主进程，但会引入第二个周期性任务） | 否 |
| 超限时直接删库重建 | 实现最简 | 丢失全部记忆，与"记住老师"的产品目标冲突 | 否 |
| 写后同步 prune（不 setImmediate） | 时序确定 | 把删除耗时压进 IPC 回调；积压时明显卡顿 | 否 |
| 写后 `setImmediate` + 有界批量（本方案） | 不阻塞、耗时可控、可单测 | 积压时不是"立刻"回到 2000，需要几轮 | **是** |

## 后果

**正面**

- 库大小有硬上限，`LIKE` 全表扫的最坏耗时被钉在 2000 行（实测检索仍 1–2ms）。
- 淘汰不改变 `write()` 的同步语义，对话链路无感。
- FTS5 由既有触发器同步，没有新增"两处维护"的风险。
- 单测覆盖三个边界：未超限（空操作）、超限（删最旧 5 行 + FTS 行数一致）、积压（单次 ≤200、多轮收敛），外加"写后自动排期"。

**负面 / 成本**

- 只按时间淘汰，早期的重要偏好（`like:咖啡`）会被后来的闲聊挤掉。
- `prune()` 仍是同步删除；虽然单次有界，但 200 行在低端机上仍可能到 10ms 量级。
- `snapshot()` 多了一个字段，`runtime.snapshot().memory` 的消费方（自检）要能接受。

**约束**

- 淘汰只允许按 `at` 升序删最旧，不得按 `id` 或随机删（顺序必须可复现）。
- 单次删除不得超过 `MEMORY_PRUNE_BATCH_MAX`。
- 不得为淘汰新增定时器；只能由 `write()` 之后排期，或显式调用 `prune()`。
- 不得手工删 FTS 行（触发器已经做了，重复删会破坏索引）。
