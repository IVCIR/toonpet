| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-10-30 |
| 决策者 | 项目所有者 |
| 关联 | `CONTRACTS.md` §3.1（托盘归 shell）、§3.2（主窗口 `focusable=false`）、§7.2（`start` 创建托盘）、§9.2（LLM 输出校验）、§9.3（提示词段 1）、§9.4（配置）、§10.1/§10.2（零成本与回环）、§11（降级矩阵）；ADR 0003（焦点策略）、ADR 0004 D9（托盘退出走 `shell.stop()`）、ADR 0015（LLM/TTS）、ADR 0016（输入条与热键）；本决策使 `CONTRACTS.md` 升至 **1.4.1**（patch：只澄清 §9.2 的清洗顺序与补 `.env` 配置来源，不改模块接口、事件、状态、intent/emotion） |

## 背景

阶段 7 之后，三件事同时卡住"真实可用"：

1. **真实 LLM 已经连上，但输出被判非法。** `qwen3:4b` 健康检查通过、一轮 3.1s 返回，可正文形如
   `**老师**，（微笑）今天也要加油哦！`，被 §9.2 的 `text 不含 Markdown/括号动作` 规则判
   `invalid_output` → 整条回复降级到兜底。表现为"LLM 好像没接上"，实际是"模型可用、格式不合规"。
   契约 §9.2 允许"从代码块或前后废话中提取 JSON"，但没有写"能不能剥离装饰"。
2. **配置散落在进程环境变量里。** `PET_TTS_PROMPT_TEXT`、CPU 超时等人手 `setx`，新终端才生效，
   且 `scripts/doctor.mjs` 与应用各读一份环境，用户很难确认"到底哪个值生效"。
   项目硬约束又明确不引入 `dotenv` 等第三方依赖。
3. **托盘一直没有落地。** 契约 §3.1 / §7.2 从第一版就把"托盘"算在 `shell` 的启动职责里；
   ADR 0004 D9 还写死了"托盘退出必须走 `shell.stop()`"。当前热键注册失败只有日志，
   用户没有退出/重载的 UI 入口。

## 决策

### D1 `.env` 加载器：自研 100 行纯字符串解析，进程环境变量优先

1. **位置与时机**：`bootstrap()` 的第一条可执行语句调用 `loadProjectEnv()`（`src/main/env.ts`），
   早于 `shell.start()` / `runtime.start()` 读取任何配置。文件固定为 `<appRoot>/.env`
   （开发期 `app.getAppPath()` 就是工程根目录；本期不做安装包/asar 形态，§13 X-8 非目标）。
2. **实现**：`src/shared/env-file.ts`，无第三方依赖、无网络、无子进程。语义与 Node 原生
   `--env-file` / `process.loadEnvFile()` 对齐：
   - `KEY=VALUE`；空行与 `#` 注释忽略；允许 `export KEY=VALUE`；
   - 单/双引号剥离，双引号内支持 `\n` `\r` `\t` `\\` `\"`；
   - 未加引号的值遇到"空白 + `#`"即行尾注释；文件内重复键后者覆盖前者；
   - **进程环境变量优先**：`process.env` 已存在的键默认不覆盖（`override:false`），
     `setx`、终端临时变量、`scripts/start.mjs` 为自检注入的值永远压过 `.env`；
   - 坏行只记 `issues` 并忽略，读取失败只 WARN——配置问题不得让桌宠起不来。
3. **可配项**：`.env.example` 列出全部变量（LLM、TTS、资产、数据目录、诊断开关）与说明；
   `.gitignore` 增加 `.env` / `.env.local`，模板入库。`.env` 中的值只记**键名**进日志，不记值。
4. **`doctor` 同语义**：`scripts/doctor.mjs` 在读取任何配置前用 `process.loadEnvFile()` 加载
   `<appRoot>/.env`（Node ≥20.12；本机 Node 24 实测"不覆盖已有环境变量"）。
   之所以不 import 应用的 TS 解析器：`doctor` 必须在 `npm run build` 之前也能运行，
   而 `dist/` 可能不存在或过期。两处共享的是**语义**（优先级、引号、注释），不是代码。
5. **影响范围**：`PET_LLM_MODEL`、`PET_TTS_REF_AUDIO`、`PET_TTS_PROMPT_TEXT`、
   `PET_TTS_FIRST_BYTE_TIMEOUT_MS`、`PET_TTS_TOTAL_TIMEOUT_MS` 等全部通过同一 `process.env` 生效；
   不需要给每个模块新增读取路径。本机 `.env` 已写入 CPU 部署的 15000 / 120000 超时。

### D2 LLM 输出清洗：先剥装饰、再严格校验；不放宽 §9.2

1. **清洗顺序**（`reply-validator.ts`）：
   1) 去 BOM；2) 剥整段三反引号围栏（可带 json 语言标记）；3) 从"纯文本 / 围栏内容 / 文本中第一个平衡的
   `{...}`"依次尝试解析（平衡扫描器正确处理字符串内的花括号与转义）；4) 对 `text` 字段剥离
   括号动作（`（微笑）`、`(摸了摸头)`、`【叹气】`，≤60 字）、Markdown 粗斜体（`***`/`**`/`*`/`__`）、
   行内反引号、标题/引用前缀、残留裸 `*`；5) 折叠空白、去掉括号消失后留下的孤立句首标点。
2. **"剥装饰"不是"改内容"**：只处理包裹层与旁白式括号，不替换可朗读的正文。代价是
   `我叫天童凯伊（Kei Tendo）。` 会变成 `我叫天童凯伊。`——括号内容一律视为非朗读旁白。
   这是为满足 §9.2"单段、无括号"付出的已知取舍。
3. **严格校验不变**：清洗后仍由 `validateReplyText` 判 1–120 字、单段、无残留
   `（）()[]{}`*#`、无 URL；残留未配对括号、URL、代码块照样 `invalid_output`。
   台词池装配 `assertValidReplyShape` **不经过清洗**，数据错误仍在启动期被拒绝。
4. **可观测**：清洗与字段修复都写进 `ValidationOutcome.repaired`
   （`output:fence-stripped` / `output:json-extracted` / `text:decorations-stripped` /
   `emotion->neutral` / `intent->none`），编排层用 WARN 记录；不影响 `Reply` 三字段。
5. **提示词同步**（§9.3 段 1，硬编码）：明确写"仅输出纯 JSON、不要三反引号包裹、不要括号动作、
   text 不要 Markdown/换行"。提示词是"降低脏输出概率"，清洗是"脏输出也能用"，两层都要。
6. **契约措辞**：`CONTRACTS.md` §9.2 的"越界处理"补一句"可先剥离装饰性包裹再提取/校验"，
   属于 patch 澄清，不新增字段、不改 `Reply`、不改事件与枚举。
   说明：§9.2 的校验实现原本由 ADR 0015 D1 落地；ADR 0004 只覆盖探针/手势通道，与文本校验无关。
   本 ADR 只补充清洗顺序与边界，不重写 ADR 0015 的其余条款（ADR 只增不改）。

### D3 系统托盘：`shell` 持有，16×16 内嵌图标，退出走 `stop()`

1. **归属**：`src/main/shell/tray.ts`（Electron 句柄）+ `tray-menu.ts`（纯菜单规格，可单测）。
   托盘只在 `shell.start()` 内创建、`shell.stop()` 内销毁；其他模块不碰。
2. **图标**：16×16 PNG data URL 内嵌在代码里（4× 超采样生成的浅蓝猫脸占位），
   不新增二进制资产、不读网络、不依赖 `nativeImage` 的文件系统路径。
   解码为空或 `new Tray` 抛错 → WARN 后继续无托盘运行，**不影响热键、输入条与桌宠**。
3. **菜单**（顺序与标签是行为契约）：
   | 菜单项 | 动作 |
   |---|---|
   | 呼出输入条 | 与全局热键共用 `openInputBar()`（同一入口，不复制逻辑） |
   | 重新加载桌宠 | `mainWindow.webContents.reload()`，只重启渲染进程，调试用 |
   | 退出 | 先 `await shell.stop()` 再 `app.quit()`（ADR 0004 D9） |
4. **焦点**：不调用 `setFocusable`、不调用 `mainWindow.focus()`；主窗口 `focusable` 全程 `false`
   （ADR 0003）。托盘菜单是系统原生菜单，关闭后焦点回到原应用；"呼出输入条"按既有约定把焦点给输入条。
5. **生命周期边界**：`stop()` 先销毁托盘再停轮询器/窗口；`window-all-closed` 仍由 bootstrap
   统一 `app.quit()`，`before-quit` 的 `quitting` 守卫保证 `stop()` 不会重入。
6. **可验收**：`shell.traySnapshot()` 返回 `{exists, menuLabels, tooltip, iconSize}`；
   输入条自检新增 3 条断言（存在、标签、16×16）。原生菜单的点击无法在自检里合成，
   "重新加载/退出"以人工点一次为准（记录在 `MODULE_STATUS` 坑位）。

## 替代方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 引入 `dotenv` | 生态标准、边界情况多 | 违反"不引入第三方依赖"；本需求只有 20 行解析量 | 否 |
| 只用 `process.loadEnvFile()`（应用侧） | 零代码 | 无解析报告（应用了哪些键/哪些坏行），无法把优先级写进日志；旧 Node 无此 API | 否（doctor 用它，应用用自研解析器） |
| 让 `.env` 覆盖进程环境变量 | "文件说了算"直观 | 与 `setx`/自检注入打架，排查时无法用一个临时变量压过文件 | 否 |
| 保持只读环境变量 | 零新增代码 | 用户必须 `setx` + 新开终端；`doctor` 与应用易看到不同值 | 否 |
| 清洗时**放宽** `validateReplyText`（允许括号） | 实现最短 | 直接违反 §9.2；括号会进入 TTS，念出"微笑" | 否 |
| 只改提示词、不做清洗 | 最贴近"模型自己守规矩" | qwen3:4b 仍会写旁白/Markdown；已在真机复现 | 否 |
| 先剥装饰再严格校验（本方案 D2） | 脏输出可用；残留问题仍拒绝；可观测 | 括号里的非旁白内容会被丢弃 | **是** |
| 托盘用真实 PNG 文件 | 可换图标无需改代码 | 新增资产与构建拷贝；当前只需占位 | 否 |
| 托盘图标用 `createFromBitmap` | 无需 base64 | 像素格式平台相关，Windows 上易出现颜色/透明异常 | 否 |
| 托盘"退出"只调 `app.quit()` | 一行 | 违反 ADR 0004 D9，轮询器/热键/托盘可能漏释放 | 否 |
| 托盘创建失败即退出 | 问题显性 | 桌宠本体明明可用，却因通知区域异常起不来 | 否 |

## 后果

**正面**

- 真实 LLM 第一次稳定接管：真机一轮 **1.7s**、`route=llm`，`（略带担忧地皱眉）` 被清洗为可朗读文本；
- 配置只有一个入口：`.env` 同时作用于应用与 `doctor`，改完重启即可，日志能看出哪些键被 `.env` 补上、哪些被进程环境压住；
- 托盘给出退出/重载/呼出输入条的 GUI 入口，热键注册失败时至少还有托盘可用；
- 清洗/修复全部落在 `repaired` 里，出问题能直接定位是"模型脏"还是"校验严"。

**负面 / 成本**

- `.env` 解析器与 `doctor` 的原生加载器是两套实现，需要在文档里锁死"同一语义"；
- 括号内容一律视为旁白（例如英文名、补充说明会被丢弃）；
- 冷启动首问仍可能超过 8s 预算而走兜底，清洗无法解决"慢"；
- 托盘是原生 UI，自检只能验证"存在 + 菜单标签 + 图标尺寸"，点击行为靠人工验收。

**约束**

- `.env` 只补空缺；不得把优先级改成"文件覆盖环境变量"。
- 不得给 `reply-validator` 增加"放宽字符集"的分支；清洗后必须仍走 `validateReplyText`。
- 台词池装配不得调用清洗函数。
- 托盘只在 `shell` 内创建/销毁；不得在 `render`/`orchestrator`/`voice` 里碰 `Tray`。
- 托盘菜单不得调用 `mainWindow.focus()` 或修改 `focusable`。
- 托盘"退出"必须先 `shell.stop()`；不得只 `app.quit()`。
- 不得为托盘新增事件、通道、状态或 `RenderState` 字段；`traySnapshot()` 是非契约内部诊断。
