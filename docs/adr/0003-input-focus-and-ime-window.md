# 0003. 输入焦点策略：独立输入窗口

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-10-27 |
| 决策者 | 项目所有者 |
| 关联 | `CONTRACTS.md` §3.2（`focusable` 行）、§3.6（P-3）；修正 1.0.0 的"临时改 `focusable`"写法 |

## 背景

桌宠主窗口必须 `focusable: false`：一个常驻置顶的宠物如果常驻可聚焦，会抢走全屏游戏、输入法、Alt+Tab 的焦点，桌宠立刻变成干扰源。

但要让用户输入文本，就需要键盘焦点。契约 1.0.0 写的是"打开输入条时把主窗口 `focusable` 临时改 `true`，关闭后改回"。Windows 上这条实测不可靠：透明窗口运行期切换 `focusable` 会引起窗口闪烁、丢失 `alwaysOnTop` 层级、输入法候选框定位异常（有时直接不出候选词）。这不是可以靠加延时或重设置顶修好的偶发问题，而是每次输入都会发生的稳定性问题。

## 决策

1. **主窗口 `focusable` 恒为 `false`，运行期禁止修改。**
2. **输入条是一个独立的 BrowserWindow**：
   - 尺寸 `260 × 44`，`frame: false`，**非透明**（`backgroundColor` 为不透明深色），`alwaysOnTop: true`，`skipTaskbar: true`，`resizable: false`；
   - `show: false` 创建一次，反复 `show()/hide()` 复用，不反复销毁；
   - 位置 = 角色头顶上方 8px，随主窗口移动而移动；
   - 内部是一个最小渲染页（`src/renderer/input/`），只含一个 `<input>` 与提示文案。
3. **打开与关闭**：全局热键 → `show()` + `focus()`；`Enter` 提交并发 `user_utterance`（`input: 'hotkey'`）→ `hide()`；`Esc` 或失焦 → `hide()`（丢弃输入）。
4. **关闭后不主动聚焦主窗口**：`hide()` 后焦点自然回到上一个前台应用，不调用 `mainWindow.focus()`，也不改主窗口任何窗口属性。
5. **输入条不设 parent**（不作为主窗口的子窗口），避免子窗口跟随导致的层级与坐标异常；位置由主进程手动跟随。
6. 输入条窗口**不做命中穿透**，它是一个正常的小窗，点它以外的地方由失焦逻辑收起。

## 替代方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 运行期切换主窗口 `focusable` | 一个窗口搞定，代码最少 | Windows 上闪烁、丢置顶、输入法异常，每次都发生 | 否 |
| 主窗口常驻 `focusable: true` | 输入最顺滑 | 抢焦点，影响全屏游戏与日常输入，违背桌宠定位 | 否 |
| 在主窗口内做 DOM 浮层 + `input.focus()` | 无需新窗口 | `focusable: false` 的窗口拿不到键盘焦点；要拿到就得改 `focusable`，回到上一条 | 否 |
| 用系统托盘菜单 / 系统对话框输入 | 不引入新窗口 | 交互丑陋，且对话框会抢焦点、打断沉浸 | 否 |
| 独立输入窗口（本方案） | 焦点隔离干净，输入法正常，主窗口属性完全不动 | 多一个窗口要管生命周期与跟随 | **是** |

## 后果

**正面**
- 主窗口全程 `focusable: false`，不会因为输入而闪烁或丢置顶。
- 输入法、候选框、中文组合输入在独立窗口里表现正常。
- 关闭输入条后焦点自动回到用户原来的应用，符合"桌宠不该打断我"的预期。

**负面 / 成本**
- 多一个窗口与一个渲染页，需要处理：创建时机、跟随移动、失焦收起、崩溃重建。
- 输入条与主窗口是两套渲染环境，共享常量需要走 `src/shared/`。
- 热键注册失败（被其他软件占用）时无法输入，需要托盘给出明确提示。

**约束**
- 禁止调用 `mainWindow.setFocusable(true)`。
- 禁止给输入条设 `parent`。
- 禁止在输入条里承载任何角色渲染或状态逻辑。
- 输入条失焦即收起，不做"未提交内容保留"（避免用户以为还在输入）。
