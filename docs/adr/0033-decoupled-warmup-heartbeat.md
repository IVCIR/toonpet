# ADR 0033：生命周期心跳与预热前置对齐（warmup 与主动性解耦）

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-11-01 |
| 关联 | 契约 **1.12.0** §2、§2.1、§3.1、§4.6、§7.6（PR-8）、§11、§12、§15；ADR 0030（presence）、ADR 0031（idle-drive）、ADR 0032（预热与托盘诊断） |
| 影响模块 | `orchestrator`（新增 `heartbeat`，删除内部的预热实现）、`runtime`（装配）、`shell`（一行闩锁）、自检 |

## 背景

ADR 0032 D3 把冷启动预热挂到了 idle-drive 的 15s 节拍上，当时自己在「后果 → 负面」里写下了
这条取舍：

> **推论（已知取舍）**：预热挂在 idle-drive 节拍上，因此 `PET_SELFTEST=1`（主动性硬关）时不预热，
> `PET_PROACTIVE_DISABLE=1` 时也不预热。

这个取舍在今天变成了两个真实的体验缺陷：

1. **关掉主动性 = 永远不预热。** `PET_PROACTIVE_DISABLE=1` 是"别打扰我"的逃生口，
   不是"别加载模型"的开关。可现状是：只要老师不想要主动插话，第一句话就永远撞冷启动
   （实测 `qwen3:4b` 首次加载约 10s，而 §9.1 ② 的硬超时是 8s → 必然 `llm_failed{timeout}` → 兜底）。
   把两个语义绑在一条节拍上，是这次要拆掉的东西。
2. **预热比"她站起来"来得太晚。** 现状是"应用启动 → 等第一个 15s 节拍 → 才开始加载模型"。
   而 VRM 加载 + 首帧只要 1–2s：她 2 秒就出现在桌面上了，模型却要等到第 15 秒才开始热。
   第 16 秒之后老师的第一句话仍然要等一个"热了一半"的模型。
   **唯一真正恰到好处的时机是 `model_ready` 本身**——模型刚加载完、她刚出现在桌面上的那一帧。

这两件事都不是"再加一个功能"，而是把已经存在的能力摆到正确的位置上。

## 决策

### D1：抽出生命周期心跳（`heartbeat`），与 idle-drive 彻底解耦

新增 `src/main/orchestrator/heartbeat.ts`，由 `runtime` 装配。它是主进程里**唯一只做生命周期任务**
的节拍器；当前它只有一件任务：冷启动预热。

| 项 | 决定 | 理由 |
|---|---|---|
| 位置 | `src/main/orchestrator/heartbeat.ts` | 它读的是 `llm` 客户端与 `presence` 端口，和 `orchestrator` 同一依赖层；不放进 `shell`（shell 不认识 LLM），也不放进 `render`（渲染进程不许发网络请求） |
| 节拍 | `HEARTBEAT_TICK_MS` = 15s | 与 idle-drive 同频但**独立**：两个定时器、两套语义、互不引用 |
| 职责 | 只有生命周期任务；**不判断是否打扰** | `idle-drive` 回答"现在能不能开口"，心跳回答"进程活着还要做什么"。混在一起就会出现本轮背景里的第 1 个缺陷 |
| 输入 | `llm`、`presence`、`host.isBusy()`、`host.isLlmDisabled()` | `host` 是两个**只读**闭包（§7.7 I-1）：心跳既不改编排状态，也不替它做决定 |
| 输出 | 1-token `/api/generate` | 与 ADR 0032 D3 完全一致：不建会话、不改熔断、不发事件、不占预算（W-1…W-4） |
| 状态归属 | `warmedUp` / `attempts` / `lastAttemptAt` 从 `orchestrator` 搬到心跳 | 迁移后编排层的 `snapshot()` **不再有** `llmWarmedUp` / `warmupAttempts`：那是心跳的事实，留在编排层就是一条会过期的镜像 |

**为什么不是"第六个模块"**：它与 `presence`（ADR 0030）同一性质——`runtime` 装配的一个内部组件，
不认识 `Reply`、不产事件、不写库、没有对外接口方法。§2 的五个模块划分不变。

#### D1.1 总闸：`PET_WARMUP_DISABLE` / `PET_SELFTEST`

新增 `src/main/heartbeat-config.ts`（不 import Electron，可单测），优先级：

1. `PET_WARMUP_DISABLE=1` → 关闭。用户逃生口：不想让任何后台请求碰本地 LLM 时用；
2. `PET_SELFTEST=1` → **硬关**。自检必须保持"零后台推理"（ADR 0031 D6 的同一理由：
   三套自检对时序与截图像素差有强断言，一次后台加载会随机改变它们的时序）；
3. 其余 → 开。

**刻意不提供** `PET_SELFTEST_WARMUP=1` 之类的开关：自检的零后台推理是**硬保证**，不是默认值。
将来真要端到端验收预热，应该像 `selftest-stubs` 那样起一个本地桩 HTTP 服务，
而不是先给自检开一个可能被 `.env` 意外打开的口子。

于是四条路径的行为被钉死：

| 场景 | 主动性 | 预热 | 自检 | 是否预热 |
|---|---|---|---|---|
| 日常默认 | 开 | 开 | 否 | **是**（`model_ready` 立刻 + 15s 节拍重试） |
| 关掉主动性 | 关 | 开 | 否 | **是** ← 本轮修的第 1 个缺陷 |
| 关掉预热 | 任意 | 关 | 否 | 否（连定时器都不建） |
| 自检 | 关（默认） | 关（硬） | 是 | **否**（零后台推理） |

### D2：`model_ready` 前置对齐——她站起来的那一刻开始预热

#### D2.1 触发点：`runtime` 注册一次性观察者

`runtime` 在装配心跳后向 `model-ready` 模块注册一个观察者，收到就 `heartbeat.warmUpNow('model-ready')`。

- `shell` 仍然是"显示路径"的消费者（`showInactive()`），职责不变；
- `runtime` 只是**读同一个事实**去驱动生命周期任务，不新增事件、不新增 IPC、不改 `RenderState`；
- `render` 依旧是唯一生产者（§6.3 / §4 的事件语义没有被碰）。

**为什么不用 `appBus.emit('model_ready')`**（第一版就写错在这里，真机验证时抓到）：
`appBus.emit` 会把事件同时转发给渲染侧（`evt:broadcast`），等于让渲染进程收到自己刚发出的事件——
一次无意义的回环；而 `model_ready` 本来就是"渲染侧上行、shell 收口"的那一个。这里要的不是广播，
是"一个事实 + 一个想知道它的组件"，所以给它一个 20 行的自包含模块（`src/main/model-ready.ts`）：
闩锁 + 一次性观察者。

#### D2.2 早到的事件：一次性闩锁（`src/main/model-ready.ts`）

`model_ready` **可能早于 `runtime.start()` 完成**：启动顺序是 `shell.start()`（建窗、装页面）→
`runtime.start()`（读配置、开库、装配编排），而渲染进程完全可能在后者跑完之前就把 VRM 加载完了
（`selftest.ts` 里 `baselineLineCount` 那条注释就是当年踩到的现场）。只订阅不补偿的话，
"最该预热的那一次"恰好会被丢掉。

取本工程已经用过两次的手法（`appBus`、`proactive-stats`）：**进程内单例**。

| 项 | 决定 |
|---|---|
| 写方 | 只有 `shell`：它本来就是 `model_ready` 的唯一消费者，收到就落一个闩锁（`noteModelReady()`） |
| 读方 | 只有 `runtime`：装配完心跳后 ①注册观察者（在线补发）②读一次闩锁（早到补发） |
| 语义 | 只记第一次（`model_ready` 正常会话只发一次；托盘"重新加载桌宠"会再发，但预热一次就够） |
| 不是 | 不是事件、不是 IPC 通道、不是 `shell` 的 setter、不经过 `appBus`（会回环）、不加 `RenderState` 字段（§6.3 N-8 / §7.7 I-2） |
| 清零 | `runtime.stop()`（同一进程内重装 runtime / 重载渲染页时从头再来），同时清空观察者 |

顺序无关性：先 `subscribe` 再读闩锁。若事件在两者之间到达，订阅回调先发一次（`warmedUp` /
`in-flight` 会挡住补发），若在订阅之前到达，则由闩锁补发。两条路都不会重复请求。

#### D2.3 为什么 `model_ready` 是正确时机，而不是"启动后立刻"

预热会占几秒 CPU（模型加载）。在 VRM 还在加载、路由还在装配时抢 CPU，会把她出场的首帧推后——
用户看得见的是"桌宠启动变慢了"。`model_ready` 是**恰好相反**的时刻：该加载的都加载完了，
CPU 空出来了，而老师的第一句话通常还在几秒之后（他得先打开应用、想起要说话）。
"她出现在桌面上"与"模型开始变热"同时发生，首问的 8s 冷启动就被抹平了。

#### D2.4 忙碌时让位，不排队

若 `model_ready` 那一刻编排层正好忙（`thinking` / 在途话语 / 正在播语音——例如重载渲染页时她正在说话），
这次触发**丢弃**、不排队：下一次心跳（≤15s）会重试。理由与 ADR 0031 的 `busy` 同源——
宁可晚 15s 热，也不在对话中途抢 CPU。

### D3：唯一一处旧规则的放宽——`model_ready` 绕过 presence 门槛

ADR 0032 D3 的第 4 条边界是"presence 读不到就不预热"：与 idle-drive 的 `no-presence` 同源，
**连"用户在不在这台机器前"都不知道时，不做任何消耗 CPU 的动作**。这条规则在 15s 心跳上保留，
`model_ready` 触发**不受它约束**：

| 触发 | presence 门槛 | 理由 |
|---|---|---|
| `tick`（15s 心跳） | 保留 | 它发生在任何时刻，读不到在场感时确实不知道老师是不是刚离开 |
| `model-ready` | **绕过** | 这一次发生在"老师刚启动进程、模型刚加载完"之后不到 2 秒——启动动作本身就是最强的在场证据。为了一个 koffi 缺失的环境让首问永远冷启动，代价远大于一次 1-token 请求 |

放宽是**有界**的：一次请求、`num_predict: 1`、最多 3 次、60s 间隔、不改熔断、不发事件、
不占预算。它不是"无视在场感"，只是承认"刚启动"这个时刻的在场证据比一次 `GetLastInputInfo` 更强。

### D4：自检仍然零后台推理，并把它变成一条断言

`PET_SELFTEST=1` 时心跳**整个不启动**：不 `setInterval`、不读 `presence`、不发请求。
不是"建了定时器但不触发"——那样仍然是一个会走动的钟，且未来很容易被改成"顺手做点别的"。
整个不建，才是可以一句话说清、也可以一条断言钉住的保证。

于是自检里新增一条断言（主链路 120 → 121 条）：

```
预热：自检默认硬关（零后台推理，ADR 0033）
  enabled === false && running === false && attempts === 0 && warmedUp === false
```

诊断读数挂在 `RuntimeSnapshot.warmup`（`HeartbeatSnapshot`）。**没有**新增 IPC、没有新增事件、
`RenderState` 未动。

### D5：本轮没有新增的东西

| 类别 | 结论 |
|---|---|
| 事件 | 无（§6.3 清单不变，`model_ready` 只是多了一个读它的人） |
| IPC 通道 | 无 |
| `RenderState` 字段 | 无 |
| 模块公共接口方法 | 无（`heartbeat.warmUpNow()` 是 `runtime` 装配的**内部**组件方法，不在任何模块的对外契约里） |
| 运行时依赖 | 无 |
| 定时器 | 净 +1（心跳 15s）。它只在"非自检且未关闭"时存在；与 16ms 轮询器、15s idle-drive 各自独立、互不引用（§12） |
| `orchestrator.snapshot()` 字段 | **删** 2 个（`llmWarmedUp` / `warmupAttempts`，迁进 `RuntimeSnapshot.warmup`） |

## 验证（真机，2026-11-01）

- 全量单测 **417 个（38 文件）** 全绿；`tsc --noEmit` 0 错。
- 四套自检全绿（exit 0）：主链路 **121/121**（含新增「预热：自检默认硬关（零后台推理）」）、
  输入条 **29/29**、语音 **30/30**、缺失模型 **4/4**。
- **真机预热验证**（两次，都用只监听回环的本地桩）：
  1. 默认配置：日志顺序为 `[heartbeat] 生命周期心跳已启动` → `[shell] 收到 model_ready` →
     `[heartbeat] LLM 预热已发出 {"trigger":"model-ready","attempt":1}`，桩收到
     `POST /api/generate { model, num_predict: 1 }`；`model_ready` 与预热请求相隔 **~10ms**。
  2. `PET_PROACTIVE_DISABLE=1`：同样的日志、同样的请求照常发生——**这就是 D1 要证明的那件事**。
  **第一版在这里是静默的**——触发点被写成 `appBus.subscribe('model_ready')`，而 `shell` 从来没有把
  这个上行事件发到总线上（它只是 IPC 的收口）。单元测试全绿也发现不了这件事，因为它只验证心跳本身。
  这条坑现在写进 D2.1 与 MODULE_STATUS。

## 后果

**正面**：

- 关掉主动性不再牺牲预热：`PET_PROACTIVE_DISABLE=1` 下首问依然有热好的模型。
- 预热与"她出现"同时开始，把首问的 8s 冷启动压到几乎不可感知（模型加载与 VRM 加载/出场动画重叠）。
- 编排层不再认识"预热"这个概念：`orchestrator` 的职责重新变成纯净的"说什么 / 什么情绪 / 什么动作"，
  预热的状态机搬进一个 60 行的独立组件，测试面从"编排层的内部状态"变成"心跳的输入输出"。
- 自检的零后台推理从"默认值"升级成"硬保证 + 一条断言"。
- 单测 +29（heartbeat 16 / heartbeat-config 6 / model-ready 12，减去迁移走的 5 条 = 净 +29），
  全部零网络（LLM 用桩，时间用注入时钟）。

**负面 / 已知取舍**：

- 定时器从一个变成两个（idle-drive + heartbeat）。它们的生命周期由 `runtime.start()/stop()` 统一管理，
  但确实比"一条节拍干两件事"多一个对象；换来的是两条语义不再互相绑架。
- `model_ready` 早到时的补偿依赖 `shell` 落闩锁：如果将来有人让 `render` 在**没有窗口**时也发
  `model_ready`（目前不可能），闩锁就永远不会被写。已写在 ADR 与代码注释里。
- `model_ready` 绕过 presence 门槛，意味着 koffi 缺失的机器上也会在启动时打一次本地请求。
  这本就是"要预热"的题中之义，但确实是对 ADR 0032 D3 第 4 条的一次有意放宽（D3）。
- 预热仍然**不保证常驻**：Ollama 默认 `keep_alive` 5 分钟，闲置后仍会卸载。
- 托盘的两行诊断没有增加"预热状态"：那是另一块 UI 语义，本轮不做（避免又一次"为了可见而加事件"）。

## 被否决的备选

| 备选 | 否决理由 |
|---|---|
| 把预热改成独立的 `setTimeout(0)` 一次性任务 | 丢掉"失败后按 60s 重试、最多 3 次"的节流，一个关着的 Ollama 会被敲穿；也没有地方放"下一次" |
| 在 `shell` 里预热 | `shell` 不认识 LLM（§2 明确"不决定说什么"），还会把 `llm-client` 拖进窗口模块的依赖图 |
| 给 `orchestrator` 加公共方法 `warmUpNow()`，由 `runtime` 调用 | 把"加载模型"塞回编排层的公共面（§7.6 只列 `respond`/`cancel`），且它和"这句话说什么"毫无关系。心跳是 `runtime` 装配的组件，接口面只在装配层 |
| 让 `shell` 轮询 `getState().modelReady` 来触发 | 引入轮询延迟与新定时器，且 `modelReady` 是状态不是事件——§6.3 已经有 `model_ready`，没有理由不看它 |
| 新增 `warmup_requested` 之类的事件 | 违反 §6.3 N-8（新增事件 = minor + 全模块评审），而这个信息只有心跳一个消费者 |
| 无条件预热（不看 busy / presence） | 会与 VRM 加载和用户在途对话抢 CPU；"预热拖慢了出场"会立刻可感 |
| 给自检加 `PET_SELFTEST_WARMUP=1` 开关 | 自检零后台推理必须是硬保证，不能是一个可能被 `.env` 意外打开的口子 |
| 保留 `orchestrator.snapshot().llmWarmedUp` 作为兼容字段 | 迁移后它就是一条会过期的镜像；诊断只有一处真相（`RuntimeSnapshot.warmup`） |
