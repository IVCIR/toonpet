## 背景

这个项目由多个独立模块对话推进，每个对话的上下文不共享。技术选型（Electron 结构、VRM 加载、本地 LLM、本地 TTS、SQLite 记忆、零成本红线）一旦只在对话里口头确定，下一个对话就会重新讨论甚至推翻。需要一个**写入仓库、按时间累积、可被引用**的决策记录，且成本必须低到愿意真的去写。

## 决策

采用 ADR（Architecture Decision Record）：

1. 每一份 ADR 记录**一个**决策，文件放在 `docs/adr/`，命名 `NNNN-kebab-case-title.md`，编号四位、从 0001 起递增，不复用。
2. ADR 只增不改。决策变化时**新写一份** ADR，并在新文件里写 `替代 #NNNN`；旧文件状态改为 `已废弃` 或 `被替代`。
3. 只有以下情况**必须**写 ADR：
   - 影响两个及以上模块的边界或接口；
   - 引入或替换运行时依赖；
   - 改变状态、事件、`intent`、`emotion` 的集合；
   - 影响成本结构（任何可能产生费用的路径）；
   - 推翻 `CONTRACTS.md` 中已有的规定（含"契约允许但平台不允许"的实现规则）。
4. ADR 四段固定为：**背景 / 决策 / 替代方案 / 后果**，不增不减。
5. ADR 被接受后，`CONTRACTS.md` 按 §15 升版本，`MODULE_STATUS.md` 的「对应契约版本」同步更新。
6. ADR 里不写实现代码，只写约束与理由；代码细节进模块本身。

## 替代方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 全部写进 `CONTRACTS.md` | 单一文件、无需跳转 | 决策理由会淹没在规范里，历史不可追溯 | 否 |
| 用 Git commit message 记录 | 零额外文件 | 不可检索、不可引用、跨对话读不到 | 否 |
| 用外部 Wiki / 在线文档 | 排版好 | 违反零成本与离线可用原则，且与仓库不同步 | 否 |
| 只靠对话记忆 | 快 | 下一个对话必然丢失，重复争论 | 否 |
| ADR（本决策） | 仓库内、可引用、增量、成本低 | 需要自律维护 | **是** |

## 后果

**正面**
- 新对话只需读 `CONTRACTS.md` + 相关 ADR 即可接续，不必复述历史。
- 决策被推翻时留有痕迹，不会出现"两张互相矛盾的规范表"。
- 成本红线有了可引用的出处（每条红线都可挂 ADR 编号）。

**负面 / 成本**
- 每次重要改动多一道写文档的工序。
- 编号与状态需要人工维护，可能出现漏写。
- ADR 过多时需要索引（见下方附录 B）。

**约束**
- 不允许"先实现、后补 ADR"。
- 不允许用 ADR 承载待办事项（TODO 进 `MODULE_STATUS.md`）。
- 状态只有四种：`提议` / `已接受` / `已废弃` / `被替代`。
